Resumen ejecutivo

Pregunta original: ¿alguna competencia de «crear bots para vencer un juego» fue sobre Teeworlds, y qué material público pre-hecho sirve a este repo? Respuesta corta: no existió una competencia formal de bots de Teeworlds (la comunidad lo descartó en 2015 por tamaño), pero sí hay un hackathon reciente con artefactos públicos (OpenEnv Hackathon SF, 7-mar-2026 → TeeUnit), un ecosistema de bots hechos por la comunidad, el mayor dataset reproducible de gameplay que existe (teehistorian de DDNet, ~TB desde 2017) y crates Rust listos para cargo add.

~15proyectos verificados con repo público
1entorno OpenEnv de TW ya publicado (TeeUnit, MIT)
~3 M runsteehistorian solo del mapa Tutorial (756 GB); DDNet graba todo desde 2017
18 mapasoficiales vanilla (dm/ctf/lms) + miles DDNet descargables
5+crates Rust de formatos TW (map/demo/snapshot/teehistorian)
Quick wins (detalle en §8): conversor .map → from_ascii con twmap (dev-tool); pathfinding tipo nheir como entrada a Brain; behaviour cloning sobre nuestros propios report.bin (gratis, ya existen); adapter OpenEnv sobre crates/gym si se quiere publicar/competir.

Competencias y hackathons de «bots que juegan» — ¿hubo sobre Teeworlds?

EventoCuándo¿Sobre Teeworlds?Material que dejó
Hilo «Yet another bot» (foro oficial)2015Se propuso una competencia estilo StarCraft AI Competition y se descartó: comunidad chica + «TW tiene poca estrategia para ser interesante». Los autores se medían informal: duelos bot-vs-bot en servers propios (BotCTF de nheir, duel 144:100 entre bots). Discusión útil sobre waypoint-graphs autogenerados desde el mapa.
OpenEnv Hackathon SF (Cerebral Valley)7-mar-2026Sí, indirectamente. Hackathon de entornos OpenEnv; el proyecto «Athens» = TeeUnit, un env OpenEnv donde LLMs/RL juegan Teeworlds 0.7.5 (4 bots en el demo). Es el único material de «competencia» real sobre TW encontrado. Repo ziadgit/teeunit (MIT), HF Space ziadbc/teeunit-env, agente entrenado ziadbc/teeunit-agent (Q-learning tabular, JSON descargable). Ver §4.
Calendario propio (31 hackathons trackeados)2026Ninguna sobre TW. La más cercana: AMD AI League Match 6 — «agente juego de estrategia» (cierra 1-dic-2026): es bots-que-juegan pero de estrategia, no Teeworlds.—
Competencias clásicas de game-AI (contexto)variosNinguna usó TW: SSCAIT/AIIDE (StarCraft), BotPrize (UT2004), GVGAI, Fighting Game AI, Battlecode, Terminal, Halite, Battlesnake, Russian AI Cup.Formato replicable si algún día se arma un «teeworlds-rs bot cup» propio.
Lectura: el nicho está vacío. Publicar crates/gym como entorno OpenEnv-compatible nos pondría como el segundo env de Teeworlds del mundo — y el único con sim determinista nativa (~256× tiempo real, ver artefacto principal). TeeUnit corre el server real de TW; el nuestro es pura sim en Rust, ordenes de magnitud más rápido para entrenar.

Bots / IA hechos por la comunidad (qué se puede portar)

ProyectoQué esAprovechable para este repo
nheir/teeworlds rama server_bot0.7 La referencia fuerte. Bots server-side en vanilla (el famoso «BotCTF»). Tres piezas: (a) pathfinder sobre grafo de triangulación generado del mapa; (b) simulación de trayectorias de proyectiles en varias direcciones — si alguna pega enemigo, dispara (prioridad Hammer>Laser>Grenade>Shotgun>Gun); (c) selección de objetivo entre pickups/enemigos/lugares random. Config sv_bot_*. Las tres ideas portan directo: A*/grafo sobre celdas libres del tilemap como entrada extra a observe() (hoy solo hay raycasts locales); rollout de proyectil reutilizando la propia sim (granada/láser ya existen); scoring de target vs. nuestro assign_targets determinista.
TeeworldsBotLib (org propia) API C++ embebible para bots server-side, diseñada para ser pura: Tick(StateIn) → StateOut, sin IO ni red ni estado oculto (estado persistente portable por struct). Debug por razones (DIR(-1, "ir a pickup")), API de dibujo (líneas/texto en coords), hot-reload de .so, metas: portable entre codebases TW/DDNet, testeable 100%, rápida. Desarrollo temprano. Valida nuestro diseño (Brain/Policy ya son funciones puras estado→Input). Ideas a robar: razones anotadas por output (el panel F3 ya muestra target/métricas; agregar «por qué» por acción), hot-reload ≈ nuestro ckpt reload, dibujo de debug ≈ nuestra línea bot→target. Sin licencia declarada en el repo → inspirarse, no copiar código.
LordSk zomb, AssassinTee ZoD2, zChaos (0.6) Bots zombie/infección server-side mencionados en teeworlds/teeworlds#1966 (el issue oficial «Add server sided bots», aún abierto, asignado a nheir). Referencia de comportamiento de persecución simple (zombies que chasean sin armas) — útil para especies tipo «carroñera» o modos PvE futuros.
infclass/teeworlds-infclassR Mod Infection mantenido (rama production). Servidores públicos corren bots de infectados (Discussion #110, may-2026: usuarios preguntan cómo activarlos → existen y funcionan). Bots de melee/persecución probados en producción contra humanos reales.
DDNetPP/DDNet++ Server DDNet con NPCs scripteados (ej. blmapchill_police.cpp — policías que persiguen jugadores marcados); el README de TeeworldsBotLib lo cita como ejemplo de bot «viejo estilo» a reemplazar. Ejemplo de bots complejos guiados por script/máquina de estados — patrón para nuestro scripted.rs del gym.
fasterthanlime/teeworlds-ai (2009, 0.5.1, lenguaje ooc) Primer intento público de AIs client-side (hooks en controls.cpp, clases AI extensibles). Histórico. Solo valor arqueológico.
chillerbot-* (familia ChillerDragon) Clientes headless/console: chillerbot-ng (DDNet headless + modo pentest anti-servers), chillerbot-h7 (0.7 headless), chillerbot-ux (cliente con warlist, auto-reply chat, password manager), -cb (chatbot), -ts (TS client). No hablan nuestro protocolo (es el real de TW), pero referencian features: warlist ≈ assign_targets/human_cap; el modo pentest ≈ nuestro wscheck con esteroides (fuzzing de chat/comandos contra el server).
KRX Client / Shalawa Client Cheat clients comerciales cerrados basados en DDNet: aimbot, TAS (grabar/replay inputs con TPS variable, rewind/forward por tick, path visualization), dummy-fly, gores-bot, «legit mode» humanizado. (a) Referencia de features para un modo replay/TAS propio del modo race (ghost de mejor run — nuestro recorder determinista ya lo permite). (b) Si el server público crece, los cheaters existen — conviene rate-limits y validación server-side temprano.

RL, entornos y datos de gameplay

ProyectoQué esAprovechable
ziadgit/teeunit («Athens», OpenEnv Hackathon SF) Env OpenEnv-compatible, MIT: server real teeworlds_srv 0.7.5 + bots que conectan como clientes UDP reales + FastAPI /reset /step /step_all /state /health /ws. TeeInput es 1:1 con PlayerInput (direction, target_x/y, jump, fire, hook, wanted_weapon — igual que nuestro Input). Obs desde snapshots. Rewards: +10 kill, −5 death, +0.1/HP daño. Modo turn-based (ticks_per_step). Docker ghcr.io/ziadgit/teeunit, notebooks y agentes de ejemplo (play_agent.py, play_llm_agent.py). Blueprint para exponer crates/gym como env OpenEnv (misma API, pero sim nativa: ~12.8 k ticks/s vs correr el juego real). Su agente publicado sirve como baseline «a superar». Su espacio de acción confirma que nuestro Input ya es el formato estándar.
meta-pytorch/OpenEnv (framework) Estándar de entornos de RL agéntico (HF): reset()/step()/state() sync/async sobre WebSocket, cada env = imagen Docker (local, cloud sandbox u HF Space), 40+ envs, expone tools por /mcp, integra TRL/torchforge/SkyRL/ART/Harbor (ejecuta Claude Code/Codex/etc. como agentes). Si se publica el gym: spec a seguir + canal de distribución (HF Spaces) + hackathons de Cerebral Valley que aceptan envs (precedente: Athens).
timakro/tmlp (2019) «Teeworlds Machine Learning Project»: fork del server TW para extraer estados + A2C con RNN en Python. Resultado honesto del autor: aprendió a no matarse solo, no aprendió a pelear (sin tuning, posibles bugs). Evidencia de que A2C crudo < ES en este dominio: nuestro OpenAI-ES antithetic sí produce kills/hooking. También un ejemplo de cómo instrumentar un server TW para estados (por si algún día se quiere comparar).
teehistorian (formato DDNet) DDNet graba todo input de todo jugador en sus servers oficiales desde 2017 — terabytes en formato ligero documentado (mensajes PLAYER_NEW/DIFF, INPUT_DIFF, FINISH…). Es posiblemente la mayor colección de gameplay reproducible que existe en videojuegos. Acceso: se pide a los admins DDNet (precedente: pati.ga «TwMillion» obtuvo 756 GB ≈ 3 M runs solo del mapa Tutorial). Datos humanos reales para imitation learning o análisis de estilo (ej. medir cuánto hookan los humanos buenos vs. nuestro hook-camping del 90 %). No es público en bulk: hay que pedirlo.
iMilchshake/teehee-extractor (Rust) Crate/binario: archivos teehistorian → HDF5 (seq, ticks, features) con move_dir, jump, fire, hook, vel_x/y, aim_angle, aim_distance; filtros AFK, teleports, cortes por muerte; paralelo por threads; meta.csv por secuencia. El pipeline de extracción ya hecho. Sus features son casi el espejo de nuestro Input — behaviour cloning directo si se consiguen los .teehistorian.
ddnet.tw/stats + ExP98/Teeworlds-DDNet-Statistics Dump público de la DB de DDNet (ranks, finishes por mapa/jugador) + notebooks de análisis. Curaduría de dificultad de mapas (finish-rate) → curriculum de mapas race por dificultad real.
Nuestro propio recorder (ya existe) crates/gym/report.rs graba snapshots World + minds + inputs por tick, con replay verificado por hash — es un «teehistorian propio». BC sobre partidas propias de inmediato (bots buenos → pre-entrenar nuevos brains); si el usuario juega por el cliente, grabar esas sesiones = datos humanos del propio juego sin depender de DDNet.

Librerías Rust y formatos

ProyectoQué esNotas
twmap (Patiga, crates.io 0.16.0) Parser/editor completo de .map (TW 0.7 y DDNet 0.6): TwMap::parse, groups/layers, GameLayer/GameTile, entities, images/sounds, MapDir, rotate/mirror/edit.
AGPL-3.0-only. NO linkear al server ni a binarios distribuidos (AGPL cuenta uso por red). Usar como dev-tool offline (map2ascii): el ASCII generado es dato, no derivado del código. Si se quisiera parse en runtime, usar libtw2 o ddnet-rs en su lugar.
heinrich5991/libtw2 La documentación canónica de formatos TW/DDNet (doc/: datafile, map, protocol, snapshot, teehistorian, map_v4.ksy de Kaitai) + crates Rust asociados (datafile, map, demo, snapshot, gamenet_*, teehistorian, packer…). Su propio doc recomienda twmap de Patiga para mapas. Referencia obligada para: leer demos/teehistorian, compat de protocolo si algún día se reabre ese scope, y spec del formato para un parser propio liviano (solo tiles+entities) sin la AGPL.
ddnet/ddnet-rs (Apache-2.0) Reescritura completa de DDNet en Rust (~100 crates): cliente, game-server, editor de mapas colaborativo en egui, legacy-proxy (compat con clientes viejos), demo playback, wasm-runtime para mods sandboxed. Referencia arquitectónica gigante y código porteable (Apache-2.0): su port del gamecore/physics, su prediction, y sobre todo su editor para Fase 7 y su wasm-runtime para el workshop (mods/mapa de usuarios sandboxeados — exactamente el problema del workshop planeado).
jxsl13/twmap (Go) Parser .map en Go con mapres embebidos y licencias por archivo detalladas (fonts OFL, etc.). Alternativa si se prefiere tool externo en vez de crate; buena referencia de licencias de mapres.
msiglreith/teebot Bot de Discord para torneos de TW (Rust, chico). Widget «torneo/ladder» futuro: pattern ya hecho.
teewebs.net / teeworlds.leaningtech.com Ports del juego real a web (emscripten/cheerp) — ya citados en las decisiones del repo. Solo como benchmark de UX/presentación.

Caveats: (a) la capa Front también lleva físicas (mismos ids, TILESLAYERFLAG_FRONT) — hay que combinarla con la game layer al convertir. (b) Los mapas DDNet reales dependen de freeze/tele/switch que no existen aquí → portarán «incompletos». Prioridad de conversión: vanilla dm*/ctf*/lms* > novice/race simples > el resto. (c) El tileset render (grass/jungle…) queda fuera del ASCII: nuestro render seguiría siendo plano; los PNG mapres están en §7 si se quiere texturizar.
